## Acceso

Abre https://poker-production-d993.up.railway.app/live. Ahora aparece un formulario: introduce el mismo usuario y contraseña de `.railway-local/access.txt`. Ya no se usa el diálogo Basic Auth del navegador en Railway. El gateway Caddy de la red local conserva su autenticación anterior.

La cookie evita repetir bcrypt al subir cada JPEG. Se firma en el servidor y la clave se deriva de la credencial privada o del secreto de sesión configurado. No se guarda la contraseña en el frontend. Rotar la credencial del despliegue sin un secreto de sesión alternativo invalida las cookies anteriores. La cookie se elimina al salir; una copia de un token ya emitido conserva su validez hasta caducar, por lo que no se debe compartir.

## Preparar una cámara

1. Inicia la cámara con el móvil fijo y horizontal.
2. Abre «Preparar mesa y reconocimiento». Si la resolución difiere, adapta las regiones y revisa cada posición sobre la imagen recibida. Una imagen vertical puede calibrarse, pero orientar el móvil de frente al monitor facilita la lectura.
3. Selecciona un perfil de cartas real o importa uno. El ZIP contiene exactamente `manifest.json` y `As.png` … `2c.png`, con las 52 cartas según códigos `23456789TJQKA` y palos `shdc`. Las imágenes deben medir entre 32 y 1024 px por lado; cada archivo hasta 2 MiB, ZIP hasta 16 MiB y contenido descomprimido hasta 64 MiB. No se admiten rutas, archivos adicionales ni ZIP cifrado.
4. El manifiesto contiene `name`, `platform`, `empty_bgr` y opcionalmente `empty_tolerance`. Usa referencias capturadas con el tema de la plataforma y un encuadre comparable. Ejemplo:

```json
{"name":"Mi mesa v1","platform":"Mi sala","empty_bgr":[20,80,40],"empty_tolerance":16}
```

5. Guarda el layout. Si ya había una captura, detén y conecta de nuevo para usar las referencias y regiones guardadas. Así no se atribuye una calibración nueva a decisiones históricas.
6. Confirma Hero y participantes en la preparación de cálculos. Los hechos de una mano nueva requieren su confirmación; no se heredan rangos o acciones anteriores como hechos actuales.

No se fabricaron referencias de una plataforma real: todavía se necesita el material de esa plataforma y la validación con el teléfono del usuario. La importación proporciona el camino para configurarlas. No hay rectificación automática de perspectiva ni modelo visual entrenado con ejemplos de una sala concreta.

## Exportar y recuperar sesiones

El resumen desbloqueado incluye descarga privada y borrado. La eliminación exige una sesión `finished`, ausencia de captura/trabajo pendiente y confirmación de su identidad. El ZIP se genera en páginas y los JPEG se leen individualmente; se eliminan los temporales al terminar. Las demás sesiones se conservan. El formato contiene JSONL por tabla y un manifiesto de versión.

Para comprobar una recuperación offline con las dependencias de backend instaladas:

```powershell
python backend/scripts/restore_session.py mi-sesion.zip recuperada.sqlite
```

`recuperada.sqlite` no debe existir. Esta herramienta no escribe en PostgreSQL ni en la base de producción. Se ha ensayado la recuperación de una sesión con snapshot y evaluaciones, y el rechazo de sobrescritura.

## Copias del despliegue

Se verificó que no había copias programadas. Al intentar activarlas, Railway respondió: `Manual backups and backup schedules are only available for Pro workspaces`. No se cambió el plan. Por tanto **no hay copias automáticas activadas**.

Como alternativa se añadió y ejecutó:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/Backup-Railway.ps1
```

El script descarga un `pg_dump` privado de la base completa, comprueba su listado con `pg_restore --list`, descarga calibración y perfiles existentes y escribe hashes SHA-256 bajo `.railway-local/backups/`. La copia del 25 de octubre se restauró en PostgreSQL 18 aislado sin errores; se recuperaron las 16 tablas de producción. No se restauró ni borró nada en Railway. Hay que repetir la copia para conservar cambios posteriores y guardar una copia fuera de este ordenador si se quiere cubrir su pérdida.

## Código y CI

`.github/workflows/ci.yml` prepara build y pruebas con PostgreSQL 18 y navegador. El workflow queda listo para ejecutarse cuando el proyecto esté en el repositorio GitHub correspondiente. El remoto existente continúa apuntando a `cryptofinanci`; no se ha publicado código ahí ni se han cambiado sus ramas o remotos.

`scripts/Snapshot-Source.ps1` mantiene un historial Git local separado en `.railway-local/source-history.git`, excluyendo credenciales y archivos privados. No cambia el índice del repositorio original. Para publicarlo en GitHub sigue pendiente elegir el repositorio correcto.
